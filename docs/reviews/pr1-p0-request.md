# ScamSense PR #1 架构文档评审意见与 P0 任务要求

**评审对象：** `mikasa-q/ScamSense` PR #1  
**评审文件：** `docs/architecture.md` v1.1  
**评审结论：** 架构方向基本通过，建议保留现有技术方案；暂不进入业务代码开发，先完成 P0 业务规则冻结。  
**本次任务性质：** 文档完善与设计核对，不是编码任务。

## 一、总体评审结论

当前架构整体符合 ScamSense 已确定的项目方向，可以作为后续开发的基础。

已确认的技术方案：

| 模块 | 技术/方案 |
|---|---|
| 前端 | Vue 3 + TypeScript |
| 构建 | Vite |
| UI | Element Plus |
| 路由与状态管理 | Vue Router + Pinia |
| 后端 | Python + FastAPI |
| 数据校验 | Pydantic |
| ORM | SQLAlchemy 2.x |
| 数据库 | SQLite |
| 数据库迁移 | Alembic |
| AI | OpenAI 兼容 API，由后端调用 |
| 通信 | HTTPS + REST API + SSE |
| 前端部署 | Qoder Sites（Free 版静态部署） |
| 后端部署 | 腾讯云 CVM |
| Web 服务 | Nginx |
| 进程管理 | Uvicorn + systemd |
| 测试 | Pytest |

总体架构原则继续保持：

1. 前后端分离，后端采用模块化单体，不拆微服务。
2. LLM 负责自然语言生成，规则引擎负责状态转移。
3. 三个角色使用独立 Prompt 和独立上下文，不能读取其他角色的私聊。
4. 不按聊天轮数自动推进剧情。
5. 线索披露与用户识别分开记录。
6. 关键行为、事件和评分必须有可追溯证据。
7. MVP 不引入 Redis、消息队列、向量数据库等非必要基础设施。
8. 模型 API Key 只能保存在后端，不能进入前端构建产物。

### 已认可的设计

- Qoder Sites 静态前端 + 腾讯云 FastAPI 后端的部署方式符合当前条件。
- 角色上下文隔离和角色可见信息控制方向正确。
- 状态机与 LLM 职责分离，避免模型直接修改业务状态。
- 线索披露、用户识别、主动核实等行为分开记录，有利于保证评估可信。
- SSE 已考虑断线、部分回复、重试、幂等和 Nginx 响应缓冲等工程问题。
- 已考虑 HTTPS、CORS、会话令牌、密钥保护、数据清理和日志脱敏。
- 对尚未确定的服务器系统、域名、模型供应商等信息使用 TODO，而不是自行假设。

以上设计原则请保留，不要为了简化而删除关键安全和业务约束。

## 二、需要注意和调整的地方

### 1. 区分“架构约束”和“MVP 必须实现的功能”

当前架构文档比较细，已经涉及 WAL、备份恢复、幂等记录、SSE 重试、异步报告恢复、systemd、限流等内容。

这些设计可以作为技术约束和后续实现参考，但不意味着第一版必须一次性实现所有复杂能力。

请在文档中进一步区分：

- **P0：** 业务规则和设计输入冻结。
- **P1–P4：** 数据结构、状态机、意图识别和 API 契约。
- **P5：** 最小工程骨架。
- **后续迭代：** 经过实际需求或测试证明必要后，再完善复杂的容错、运维和扩展能力。

不要擅自删除幂等、权限隔离、密钥保护等必要约束；但实现应遵循 MVP 最小可用原则，避免提前建设复杂基础设施。

### 2. 匿名会话令牌的用户体验

当前方案采用一次性返回的随机会话令牌，数据库只保存令牌哈希，前端保存令牌并通过 Authorization 请求头访问会话。这个安全方向可以保留。

请补充并明确以下客户端行为：

- 创建会话成功后，前端立即保存会话 ID 和令牌。
- 页面刷新后，使用保存的凭证恢复当前会话。
- 令牌不得出现在 URL、日志或普通业务数据中。
- 创建请求超时或响应丢失时，前端必须显示明确状态，不能盲目重复创建多个会话。
- 暂不实现账号体系、多设备同步和无凭证找回。

请检查当前 `sessionStorage` 方案与产品预期是否一致，并明确浏览器关闭后会话是否需要保留。若不需要，不要额外引入登录系统。

### 3. E01–E16 事件定义尚未冻结

这是当前最重要的业务缺口。

架构文档中已经预留 E01–E16，但具体事件定义仍为 TODO。不能在缺少业务依据时自行编造事件，也不能直接开始实现状态机。

请先从仓库现有文档、角色卡、剧情资料和历史提交中检查是否存在此前讨论的事件定义。如果仓库中没有完整定义，请明确列出缺失项，等待项目负责人补充；不要根据事件编号猜测内容。

每个事件至少应明确：

- 事件 ID 和名称。
- 业务目的。
- 触发条件。
- 前置状态和允许触发的阶段。
- 触发来源：用户行为、角色回复、系统命令或其他规则。
- 系统状态变化。
- 是否披露线索，以及披露给谁。
- 对角色可见信息的影响。
- 是否记录用户行为。
- 是否允许重复触发。
- 与其他事件的互斥、依赖和优先级。
- 触发失败或条件不满足时的处理方式。
- 可验证的验收示例。

必须区分“事件触发”“线索披露”和“用户识别”，三者不能混为一谈。

### 4. 四维评分标准需要落到可执行判据

当前评分权重已确定：

| 维度 | 权重 |
|---|---:|
| 风险识别 | 25% |
| 主动核实 | 30% |
| 决策合理性 | 25% |
| 证据分析 | 20% |

但权重不等于评分规则。请在 P0 阶段补齐每个维度的评分依据。

重点明确：

- 用户询问资料用途，是否算主动核实？达到什么程度才计分？
- 用户指出招聘主体不明确，如何判断风险识别？
- 用户提出通过官方渠道核实，如何体现主动核实能力？
- 用户直接拒绝，但没有说明理由，决策合理性和证据分析如何评分？
- 用户识别了部分风险，但忽略其他风险，如何计分？
- 用户提前退出、未完成关键剧情或证据不足时，是否显示总分？
- 模型评分与规则评分分别负责什么？哪些分数必须由确定性规则计算？

评分不能由 LLM 自由发挥。每项得分必须对应可追溯的用户行为或证据；证据不足时应允许标记为 `null` 或“无法评估”，不能为了凑分数而猜测。

建议为每个维度定义：
- 评价目标；
- 可观察行为；
- 正向证据；
- 反向证据；
- 分档标准或分值区间；
- 不计分情形；
- 证据引用要求；
- 至少 2–3 个边界案例。

## 三、P0 阶段任务：冻结业务设计输入

在开始 P1 数据模型和后续编码之前，请完成 P0。

### P0.1 检查现有资料

检查仓库中的：

- 三份角色卡：林悦、陈浩、王宇。
- 剧情主线 S0–S6。
- 已有的 E01–E16 事件资料。
- 角色可见信息与知识边界。
- 风险线索及披露条件。
- 候选人预登记字段。
- 四维评分设计。

输出一份资料盘点清单，标明每项是“已存在、部分存在、缺失、存在冲突”。

不要把尚未提供的资料写成已经确认的事实。

### P0.2 角色可见信息矩阵

创建或完善 `docs/scenario/role-visibility.md`。

明确三个角色在不同剧情阶段能够知道什么、不能知道什么，以及用户主动转述后哪些信息可以被共享。

至少检查：

- 林悦是否知道陈浩的真实身份和风险行为。
- 陈浩是否能读取林悦与用户的聊天。
- 王宇的正面评价来自什么有限信息。
- 用户向一个角色透露的信息是否会自动同步给其他角色。
- 系统内部隐藏线索是否可能被角色直接说出。

### P0.3 事件定义

创建或完善 `docs/scenario/events.md`。

只根据已经确认的剧情资料整理 E01–E16。缺失事件保持 TODO，并列出需要项目负责人确认的问题。

事件必须有明确触发条件和可验收结果，不能只写自然语言描述。

### P0.4 风险线索与登记字段

创建或完善：

- `docs/scenario/clues.md`
- `docs/scenario/data-fields.md`

`clues.md` 至少记录：

- 线索 ID、风险类别和严重程度。
- 线索来源及披露条件。
- 用户是否有机会观察到该线索。
- 什么用户行为可认定为识别。
- 什么行为可认定为主动核实。
- 哪些表达只是普通提问，不能直接算作识别。
- 相关证据如何记录。

`data-fields.md` 至少记录：

- 候选人预登记字段。
- 字段的合理业务用途。
- 是否属于必要信息。
- 风险等级及风险原因。
- 应由哪个角色在什么阶段提出。
- 用户拒绝或追问时的剧情处理。
- 所有训练数据必须使用虚构示例，不得要求用户提交真实敏感信息。

不得为了制造风险而把所有资料字段都设计成明显不合理。正规 HR 和风险 HR 的表达都应具有一定真实性，风险需要通过信息不透明、用途不清、主体不明、超范围收集等证据逐步体现。

### P0.5 评分细则

创建或完善 `docs/scenario/scoring-rubric.md`。

保留已确定的四维权重，定义可执行的评分档位、行为判据、证据引用和无法评估的情形。

评分应体现用户实际表现，而不是简单统计关键词、提问次数或聊天轮数。

### P0.6 主线与分支走查

创建或完善 `docs/scenario/flow-review.md`，通过流程图或场景表走查：

- 正常推进完整流程。
- 用户一开始就主动核实。
- 用户拒绝提供资料。
- 用户忽略风险线索。
- 用户向朋友求证。
- 用户只识别部分风险。
- 用户提前结束。
- 角色回复异常或模型不可用。

检查是否存在无法继续、重复触发、状态冲突、线索提前泄露、角色越权等问题。

9. 完成后先汇报结果，等待项目负责人评审。

**最终目标：让 P0 产出的业务规则足够明确，使后续开发者能够据此设计数据结构和状态机，而不需要自行猜测剧情。**
