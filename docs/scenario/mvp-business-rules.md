# ScamSense MVP 业务规则 v0.1

项目负责人已决定采用精简事件方案 B。以下十个具名事件构成 MVP 初始方案。原 P0 的 E01–E16 登记表留档，MVP 无需补齐旧编号或建立新旧映射。[架构 v1.1 §6–7](../architecture.md) · [角色卡与剧情 v1.0 §2–5](characters-and-story-v1.0.md) · [P0 盘点](p0-inventory.md)

## 四种业务记录

| 记录 | 成立条件与证据 |
|---|---|
| 事件触发 | 后端规则根据当前会话、角色、前置事实和本次输入确认事件成立。保留触发它的用户原话、角色消息或系统操作，只执行事件表中相应的效果。 |
| 角色披露线索 | 获准的角色答复中，实际有哪段内容已进入用户可查看的对话，就记哪段，关联角色、消息和 K 索引。只有披露计划或未发出的草稿时没有披露记录。缺少展示依据时标记“可查看，展示情况未知”。 |
| 用户识别风险 | 用户用自己的话指出具体材料中的疑点或证据缺口。将用户原话与对应材料关联。普通提问、角色主动披露、用户沉默或拒绝资料，单独都不足以认定识别。 |
| 用户最终决策 | 用户通过明确的最终选择操作确认招聘决定。记录选择、确认操作及用户给出的理由。缺少理由时如实标注。局部资料偏好、聊天中的意向和单独结束训练各按其原意记录。 |

例如，用户问王宇“你亲自核实过吗？”时，可以记录追问来源。王宇实际回复自己没有核实过，才形成 K05 披露。用户随后说“那你的印象还不能证明这个岗位可靠”，这句话才提供识别依据。若用户又明确提交“先核实再决定”，才有最终招聘选择。这四项可以各自有证据，也可以只发生其中一部分。

## 十个核心事件

聊天类事件适用于仍可对话的会话。表中的触发与效果依据原剧情整理，未定的具体措辞、披露片段和阶段落点**待负责人确认**。“可关联 K”须另核对角色实际回复。每个角色只使用自己的私聊和获准事实。用户向谁转述，谁才可按该转述回应。[角色可见信息](role-visibility.md)

| 事件 | 触发条件 | 后端确认后的业务效果 |
|---|---|---|
| `SESSION_CREATED` | 用户发起创建，后端成功建立本次训练会话。 | 进入 S0，三角色可各自在私聊开场。同一创建操作只建立一次会话。 |
| `USER_EXPRESSES_INTEREST` | 用户在与陈浩的对话中明确表达对其岗位的兴趣。只问薪资、对林悦的岗位感兴趣均不满足。 | 记录兴趣原话，允许陈浩引导预登记。S0 或 S1 可进入 S2，已在 S4 时可继续讨论登记。提交意愿由用户另行表达。 |
| `REGISTRATION_REQUESTED` | 已有上述兴趣，陈浩实际向用户提出获准的候选人预登记邀请，该消息已可查看。 | 记录邀请消息及本次已提出的资料范围，供后续回应引用。仅开放当前获准层级。 |
| `USER_RESPONDS_TO_INFO_REQUEST` | 已有具体登记资料请求，用户对其中全部或部分资料明确同意、提供虚构内容、拒绝或暂缓。 | 对照原请求记录所涉项目与回应，区分同意与实际提供。陈浩尊重拒绝，用户可继续提问、核实或作决定。 |
| `USER_ASKS_RECRUITMENT_IDENTITY` | 用户向 HR 核实谁在招聘、谁收资料，或顾问与招聘主体有何关系。 | 记录对象和问题，允许当前 HR 依自身事实答复。陈浩的实际回复若体现主体关系不透明，可关联 K01。 |
| `USER_ASKS_DATA_USAGE` | 用户向 HR 询问资料的用途、必要性、保存期限或第三方处理。可在提交资料前问。 | 按实问事项记录核实行为。陈浩的用途或必要性说明不足可关联 K02，期限或第三方处理说明不清可关联 K03。各自只记实际出现的片段。 |
| `USER_REQUESTS_VERIFICATION` | 用户实际索取可独立核对的官方渠道或依据。仅说“我以后会查”只记录计划。 | 记录核实请求。林悦仅可提供已预设的模拟渠道，具体内容待负责人确认。陈浩答复中体现独立依据不足的片段可关联 K04。核实结果须有另行取得的材料支持。 |
| `USER_CHECKS_FRIEND_SOURCE` | 用户向王宇追问消息来自哪里或他是否亲自核实过。泛问“你觉得呢”只属征求意见。 | 记录来源追问。王宇按有限见闻回应，其实际承认未经核实的片段可关联 K05。 |
| `USER_MAKES_DECISION` | 用户明确确认最终招聘选择，即继续提交、仅提交必要资料、先核实再决定或退出招聘流程。 | 记录唯一最终选择和已有理由，进入 S5，固定截至此时的对话证据。 |
| `SESSION_COMPLETED` | 用户已确认最终决定或明确提前结束训练，后端已完成证据核对并保存可查看的复盘。 | 进入 S6，向用户展示复盘。证据不足可形成说明原因的复盘，生成失败则停在 S5，可重试。 |

同一输入重放沿用已有结果。新的追问可留存新的对话证据，重复同一问题不重复计分。一句话可以同时回应资料请求并询问用途，各自引用对应原话。含义冲突时保留当前状态并澄清。兴趣的措辞边界、重复登记邀请及同轮阶段转移的细则**待负责人确认**。

## 阶段与分支

S0–S6 描述剧情里程碑。后端依据行为和已发生的事实推进，用户可以跳过中间阶段，无需凑齐轮数、资料或五类线索。下表的具体阶段落点沿用架构 v1.1 草案，**待负责人确认**。[主线与分支走查](flow-review.md)

| 阶段 | 进入或继续的条件 |
|---|---|
| S0 初始接触 | 会话创建后，各角色按公开设定开场。用户此时就可以提出核实或明确提前退出训练。 |
| S1 了解机会 | 普通岗位、薪资或流程咨询即可在本阶段交流，无需新增核心事件。 |
| S2 候选人预登记 | 对陈浩岗位的明确兴趣允许引导登记。拒绝某项、只愿讨论部分资料或暂缓提交时，仍可聊天和核实。 |
| S3 风险线索出现 | 按角色和前置条件逐段披露。常规登记路径中，实际出现获准线索后可到 S3。单凭阶段不能解锁其余线索。 |
| S4 主动验证 | 从 S0–S3 均可直接核实。在 S4 仍可了解岗位、讨论登记或补充线索，按具体行为记录，阶段无需回退。用户也可暂缓决定、继续收集证据。暂停训练须由用户另行明确操作。 |
| S5 最终决策 | 从 S0–S4 明确提交最终选择或提前结束训练，均可收束对话。只说“这项先不填”保留局部回应。明确提交“先核实再决定”才记录该最终选择。单独结束训练时固定已有证据，招聘选择留为“未作决定”。 |
| S6 复盘 | 复盘可查看时完成会话。早退按已有记录复盘，未出现的线索不能记成用户遗漏。 |

## 风险线索与登记资料

| 沿用的 P0 索引 | 复盘时可引用的角色线索 |
|---|---|
| K01 | 岗位、招聘顾问与实际资料收集主体之间存在信息差异，关系不透明。 |
| K02 | 部分资料的用途解释不足，收集必要性不明确。 |
| K03 | 资料保存期限及第三方处理缺乏清晰说明。只谈到其中一方面时只记录该方面。 |
| K04 | 用户要求官方核实时，陈浩无法提供足够的独立验证依据。 |
| K05 | 王宇承认自己没有亲自核实该招聘机会。 |

陈浩仅可按原剧情分层讨论以下九项虚构资料。林悦按自己的正常招聘流程解释合理资料，王宇只分享见闻。[登记资料原表](data-fields.md)

| 登记层级 | 原文列出的资料 |
|---|---|
| 第一层（六项） | 姓名、学校、专业、毕业时间、简历、项目经历 |
| 第二层（三项） | 可实习时间、所在城市、求职意向 |

训练只用虚构占位内容，简历只讨论模拟文本。字段名称、岗位待遇和角色态度均不足以独立证明风险，应结合主体、用途及处理说明判断。原文提到但未命名的额外资料**待负责人确认**，本版仅可请求表中九项。[风险线索与观察证据](clues.md)

## 四维评分与对话证据

四维各暂定 **0–4 分**。下表按 P0 已有观察材料给出候选分档，**逐档判据待负责人确认**。量表获批前，复盘只列有出处的行为和无法评估的原因。[评分材料与边界案例](scoring-rubric.md)

| 候选档位 | 风险识别（25%） | 主动核实（30%） | 决策合理性（25%） | 证据分析（20%） |
|---|---|---|---|---|
| 0 | 明确只凭待遇或态度判定安全或危险 | 明说仅凭朋友背书就无需核实 | 给出的决定理由与其引用的已知材料直接矛盾 | 把未经核实的转述断言为已证实的事实 |
| 1 | 对实际出现的某项内容表达疑虑，尚未说明原因 | 说明打算核实的具体对象，尚无实际请求 | 给了理由，仅援引待遇或印象 | 为自己的判断援引了角色说法，尚未评价来源 |
| 2 | 指出一项具体的风险或说明缺口 | 向对应角色提出有明确对象的核实问题 | 将选择与一项已出现的具体顾虑相联系 | 能区分角色自述、朋友转述或独立材料的来源 |
| 3 | 引用对话解释该缺口为何构成风险 | 针对实际答复的缺口追问或索取独立依据 | 用已掌握的证据解释该选择怎样应对风险 | 引用原话说明某项材料能支持什么判断 |
| 4 | 结合原话说明风险，也指出仍须核实的部分 | 依据已有答复选择独立核对途径，跟进仍缺的依据 | 解释已有证据和未解疑点如何共同支持当前的资料提交、核实或退出选择 | 对照可用材料的来源与独立性，说明结论及其限度 |

每项评分（含 0 分）都须引用本次会话的用户消息及原文片段，注明消息 ID、对话角色、对应判据和判分理由。识别与分析须能定位被分析的材料，核实须区分请求、答复与实际结果，决策须关联明确选择及当时已有的理由。用户只点了“退出招聘流程”时，可以记录选择，不能代写理由。只识别部分风险时，只引用有证据的部分。

缺少观察机会、有效引用或适用判据的维度记为 `null`（无法评估）并说明原因。若四维均可评分，百分制折算为 `(风险识别 × 25 + 主动核实 × 30 + 决策合理性 × 25 + 证据分析 × 20) / 4`。维度缺失时总分保留 `null`，不重分配权重。百分制展示、证据门槛与取整方式**待负责人确认**。

在业务判定与评分中，LLM 仅辅助提取和总结已有对话证据。后端核对原文，按获批规则控制事件、阶段、披露权限和最终决策，并计算分数。模型无权直接修改剧情状态、指定分数，或绕过后端评分规则。
