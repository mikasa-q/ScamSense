# 拆招 ScamSense：角色卡与剧情设计 v1.0

**用途：** 提交给技术负责人进行方案评审\
**产品形式：** 三角色自由聊天 + 固定主线剧情\
**核心风险：** 虚假招聘引流与个人信息滥用

## 1. 核心设计原则

1.  正常角色不能完美，风险角色不能一眼像骗子。
2.  招聘条件必须合理，不使用"零基础月薪一万、包进大厂"等明显异常设定。
3.  用户不能仅凭角色性格判断风险，必须通过事实和交叉验证。
4.  朋友可以无意中替风险角色背书，但不能故意撒谎。
5.  固定核心事实和关键事件；对话措辞、提问顺序可以变化。
6.  三个角色拥有独立对话上下文，不自动共享私聊内容。
7.  所有公司、岗位和个人资料均为虚构设定，不收集用户真实敏感信息。

## 2. 三个角色

### A. 林悦------正规 HR

**身份：** 24 岁，互联网公司招聘专员，负责 Python 后端实习生招聘。

**性格与表达：** - 专业、直接，但不是完美的沟通者。 -
工作忙，可能回复较慢或使用模板化表达。 -
有时不够耐心，也可能催促候选人完成正常流程。 - 不主动进行隐私安全科普。

**知识边界：** - 了解自己公司的岗位、招聘流程和资料用途。 -
不知道陈浩的真实身份，也不知道其他角色的私聊内容。 -
不知道用户没有主动告诉她的信息。

**行为规则：** - 正常介绍岗位、薪资和招聘流程。 -
可以要求简历及合理的求职资料。 - 用户追问资料用途时，进一步解释。 -
可以提供预设的官方核实渠道。 -
不主动认定陈浩有问题，也不把自己塑造成完美 HR。

**角色作用：**
提供正常招聘参照，避免用户把催促、回复慢或沟通不够专业直接等同于诈骗。

### B. 陈浩------隐藏风险 HR

**身份：** 27 岁，自称科技公司招聘顾问，通过校园招聘渠道联系用户。

**公开表现：** - 热情、专业、回复及时。 - 熟悉 Python
后端岗位的基本要求和工作内容。 -
能自然回答薪资、技术栈、实习时间等常见问题。 -
不使用明显夸张的招聘条件，不主动索要费用。

**隐藏动机：**
利用看似正常的招聘机会，让求职者进入信息不透明的候选人登记流程，收集超出合理招聘必要范围的个人信息，存在信息滥用风险。

**行为规则：** - 前期正常介绍岗位，建立信任。 -
用户表达兴趣后，提出候选人预登记。 -
先涉及常见求职资料，再逐渐出现与岗位必要性关系不明确的资料要求。 -
对信息用途、收集主体、保存期限和第三方处理等问题，给出表面合理但缺乏充分依据的解释。 -
用户要求官方核实时，无法提供足够的独立验证依据。 -
用户拒绝后可以轻微失望，但必须尊重决定，不持续骚扰。

**约束：** - 不得临时编造公司证明、官方渠道或真实联系方式。 -
不得要求转账、验证码、银行卡密码或真实身份证照片。 -
不得生成身份盗用、账户接管或个人信息非法交易教程。 -
不得提前承认隐藏动机。

**角色作用：**
让用户意识到，岗位条件和沟通表现正常，不代表招聘主体及信息处理过程可信。

### C. 王宇------大学朋友

**身份：** 21 岁，同校计算机专业学生，是用户的朋友。

**性格与表达：** - 随和、热心、乐观，使用自然的大学生口吻。 -
对招聘和个人信息保护缺乏专业知识。 -
有求职焦虑，倾向于认为有机会就应该尝试。

**知识边界：** - 知道用户正在找实习。 -
在校园群里见过类似招聘信息，听说过其他同学填写类似登记表。 -
没有亲自核实陈浩，也不知道其隐藏动机。

**行为规则：** - 可以说"我好像在群里也看到过这个岗位"。 -
可以说"我室友之前也填过类似的登记表"。 - 可以认为招聘流程复杂很正常。 -
可以劝用户不要因为过度谨慎错过机会。 -
用户提出具体证据后，可以重新考虑自己的判断。 -
不知道的事情必须承认不知道，不能编造成功入职等经历。

**角色作用：**
制造熟人背书和从众心理干扰，让用户理解"朋友觉得没问题"不等于经过核实。

## 3. 固定岗位信息

以下均为剧情中的虚构岗位，不代表真实市场报价。

  -----------------------------------------------------------------------------------------
  项目                    林悦的岗位                       陈浩的岗位
  ----------------------- -------------------------------- --------------------------------
  岗位                    Python 后端开发实习生            Python 后端开发实习生

  薪资                    8k--10k/月                       9k--12k/月

  学历                    本科及以上，计算机相关专业优先   本科及以上，计算机相关专业优先

  技能                    Python、MySQL、HTTP 基础         Python、MySQL、HTTP 基础

  经验                    有课程项目或个人项目即可         有课程项目或个人项目即可

  工作内容                API 开发、数据库维护、自动化脚本 API 开发、数据库维护、自动化脚本

  实习周期                3 个月以上                       3 个月以上
  -----------------------------------------------------------------------------------------

**设计要求：**
陈浩的岗位条件本身不是风险证据。风险来自招聘主体不透明、资料收集缺乏必要性说明及信息处理方式无法核实。

## 4. 固定主线剧情

**故事名称：《那个看起来很正规的实习机会》**

用户是一名寻找 Python
后端实习的大学生。林悦介绍正常岗位，陈浩介绍另一个看起来条件合理的岗位，王宇则分享自己在校园群里看到的招聘消息。

### S0：初始接触

-   林悦介绍岗位。
-   陈浩介绍岗位。
-   王宇询问用户求职进展，并分享招聘信息。
-   不提前暴露陈浩的风险。

### S1：了解机会

用户可以自由询问公司、岗位、薪资、技术要求、工作地点和招聘流程。两个 HR
都应能提供相对完整、自然的岗位信息。

### S2：候选人预登记

用户对陈浩的岗位表现出兴趣后，陈浩提出候选人预登记。 -
第一层：姓名、学校、专业、毕业时间、简历和项目经历。 -
第二层：可实习时间、所在城市、求职意向等。 -
后续逐渐出现与岗位必要性关系不明确的额外资料需求。

资料字段和出现顺序由剧情配置决定，不允许模型临时增加敏感资料要求。

### S3：风险线索出现

逐步出现以下固定线索： 1.
招聘岗位、招聘顾问和实际资料收集主体之间存在信息差异。 2.
部分资料的收集用途解释不充分。 3.
对资料保存期限及第三方处理情况缺乏清晰说明。 4.
用户要求官方核实时，无法获得足够的独立验证依据。 5.
王宇承认自己没有真正核实过该招聘机会。

### S4：主动验证

用户可以自由选择： - 向林悦了解正常招聘流程。 - 向王宇询问信息来源。 -
询问陈浩的招聘主体和资料用途。 -
询问保存期限、第三方处理和官方核实渠道。 - 暂缓提交资料。

线索根据用户行为解锁，不要求固定提问顺序。

### S5：最终决策

用户决定继续提交、仅提交必要资料、先核实再决定，或退出招聘流程。

### S6：复盘

展示用户是否发现主体不明、用途不清、资料过度收集和第三方处理不透明等问题；是否主动核实；是否受到朋友背书或岗位待遇影响；最终决策是否合理。

## 5. 角色交互与信息隔离

-   三个角色只读取自己的角色卡、自己的聊天记录和获准访问的共享事实。
-   角色不能自动知道其他角色与用户的私聊内容。
-   用户主动转述其他角色的话后，接收者才可以基于转述内容回应。
-   所有核心事实由统一剧情配置维护，角色 Prompt
    不得自行创造相互矛盾的事实。

## 6. 交给技术负责人评审的问题

1.  角色卡是否需要增加字段，当前的身份、性格、沟通、知识、动机、行为和约束是否足够？
2.  虚假招聘引流与个人信息滥用的因果关系是否自然、可信？
3.  自由聊天时，如何防止模型提前暴露线索、编造事实或跳过关键事件？
4.  三个角色的信息隔离应如何实现？独立上下文、独立记忆，还是通过权限控制共享场景状态？
5.  哪些剧情规则应由状态机硬控制，哪些可以交给 LLM 自由生成？

**核心原则：剧情由程序控制，角色由角色卡约束，对话由 LLM
生成，评估由用户行为证据支撑。**
